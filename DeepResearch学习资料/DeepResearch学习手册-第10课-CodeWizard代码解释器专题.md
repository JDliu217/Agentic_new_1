# DeepResearch 学习手册：第 10 课

## CodeWizard 代码解释器专题

你之前问过两个关键问题：代码解释器能力到底由 LLM 决定还是由执行环境决定？本地设计 Agent 时应该调用 API 还是自己写编译器？这节课用当前项目的 `CodeWizard` 回答这两个问题。

---

## 1. 先给结论

代码解释器不是一个单独的“会写代码的模型”，而是一条组合链路：

```text
LLM
  → 生成代码和执行意图
执行环境
  → 检查、运行代码并返回输出
Agent
  → 把问题、状态、代码、错误和结果串起来
```

因此能力由两部分共同决定：

```text
LLM 决定“代码能不能生成得合理”
执行环境决定“代码能不能真实运行、能访问什么、是否安全”
```

还要加上 Agent 的编排质量：它决定什么时候执行、把什么数据传进去、失败后怎样修复、怎样把结果写回研究状态。

---

## 2. 当前项目的实现在哪里

文件：

```text
backend/app/service/deep_research_v2/agents/wizard.py
```

类：`CodeWizard`

它的职责不是从零实现 Python 语言，而是：

1. 读取研究状态中的数据点和需要图表的章节。
2. 调用 LLM 生成 Python 分析或绘图代码。
3. 清理 LLM 返回的 Markdown 代码围栏和转义字符。
4. 用 `compile()` 做语法预检查。
5. 用规则拦截明显危险模式。
6. 在白名单 globals 中执行 `exec()`。
7. 捕获标准输出、错误输出和 matplotlib 图片。
8. 把执行记录和图表写回 `ResearchState`。
9. 执行失败时把错误交给 LLM，自动修复并重试。

---

## 3. LLM 负责什么

LLM 负责根据研究上下文生成代码，例如：

```python
years = [2022, 2023, 2024]
sales = [688, 949, 1200]
plt.bar(years, sales)
plt.title("新能源汽车销量")
```

它可以：

- 选择合适的图表类型。
- 把自然语言分析目标转换成 Python。
- 解释异常并尝试修改代码。
- 根据数据生成分析思路。

它不能自动保证：

- 数据一定真实。
- 代码一定没有安全问题。
- 代码一定符合当前 Python 环境。
- 代码一定只访问允许的数据。
- 生成的结论一定没有统计错误。

所以 LLM 是代码生成者，不是安全执行器，也不是数据真实性裁判。

---

## 4. 执行环境负责什么

执行环境决定代码实际能做什么。至少包括：

| 能力 | 由什么决定 |
|---|---|
| Python 版本 | 运行环境 |
| 可导入的库 | 安装的依赖和白名单 |
| 可读取的文件 | 文件系统权限 |
| 是否能访问网络 | 网络策略 |
| CPU、内存、时间 | 资源限制 |
| 是否能启动子进程 | 操作系统和沙箱权限 |
| 输出图片如何保存 | 执行器和图表协议 |

同一个 LLM 生成的代码，在不同执行环境中结果可能完全不同。

例如代码中出现 `pandas`，如果环境没有安装它，LLM 再聪明也无法让当前进程导入成功；如果环境允许访问整个磁盘，代码的风险也会高于只读临时目录的容器。

## 5. 当前项目的执行流程

可以把 `CodeWizard` 简化成下面这张图：

```text
ResearchState.data_points
          ↓
        LLM
          ↓ Python 字符串
    清理和 compile()
          ↓
     危险规则检查
          ↓
  受限 globals + exec()
      ↙          ↘
 stdout/stderr   PNG 图片
      ↓             ↓
code_executions  charts
          ↘       ↙
       ResearchState
```

### 5.1 `compile()` 是什么

`compile()` 把 Python 源码转换成可执行代码对象，并在语法不合法时抛出异常。

它能发现：

- 括号不匹配。
- 缩进错误。
- 语法关键字错误。

它不能证明：

- 代码安全。
- 变量运行时一定存在。
- 结果一定正确。
- 没有资源消耗攻击。

### 5.2 `exec()` 是什么

`exec()` 会执行字符串形式的 Python 代码。当前项目传入受限的 globals，并尝试通过白名单和规则减少风险。

但它仍然发生在后端 Python 进程中，所以不能把它当成强隔离边界。

---

## 6. 当前简化沙箱的局限

源码注释已经明确说明这是简化沙箱。原因包括：

1. 正则过滤可能漏掉变形写法。
2. 正则过滤也可能误伤正常代码。
3. Python 对象和运行时能力很复杂，单靠受限 globals 很难证明完全隔离。
4. 无限循环、超大内存和超长计算可能拖垮进程。
5. 进程内执行出现严重错误时，可能影响整个后端服务。
6. 文件和网络权限如果没有操作系统级隔离，仍可能被绕过。

所以当前 CodeWizard 适合作为学习和受控演示实现，不适合作为面向不可信用户的生产级代码执行服务。

---

## 7. 失败后的自动修复

当前流程大致是：

```text
第一次生成代码
  → 编译或运行失败
  → 收集错误信息
  → 让 LLM 根据错误修改代码
  → 再次检查和执行
  → 最多重试 3 次
```

这叫自修复，但它不是保证成功：

- 错误可能来自数据格式，而不是代码语法。
- LLM 可能反复生成同一种错误。
- 修复后的代码可能引入新风险。
- 重试会增加模型调用成本和延迟。

工程上应该记录每次尝试，包括代码、错误、耗时和最终结果。项目使用 `state['code_executions']` 保存执行记录。

## 8. 本地 Agent 应该自己写解释器吗

通常不应该自己实现 Python 编译器或解释器。Python 语言解释器本身已经由 CPython 等成熟项目实现，自己重写会产生巨大的工作量和安全风险。

本地 Agent 应该做的是选择执行方案：

### 方案 A：调用已有代码执行 API

适合快速验证和低运维场景。你把代码和输入数据发送给服务，拿回输出。

需要关注：

- API 是否允许上传数据。
- 数据是否会离开本地。
- 运行时、库和版本是否满足需求。
- 成本、限额和延迟。
- 服务方的安全和隐私策略。

### 方案 B：本地 Docker 执行服务

适合希望控制数据和运行环境的团队。每次任务启动受限容器，挂载临时目录，限制 CPU、内存、时间和网络，执行完销毁。

### 方案 C：专用沙箱或代码执行服务

适合生产环境和不可信用户。使用成熟的隔离技术处理系统调用、文件系统、网络和资源限制。

### 方案 D：当前项目的进程内简化实现

适合教学和受控内部使用。实现简单，但安全边界弱，不能直接升级成公网生产方案。

---

## 9. 选择方案的判断表

| 场景 | 推荐 |
|---|---|
| 只是做 Demo | 现有 API 或受控简化执行器 |
| 个人本地学习 | 本地 Python 子进程或 Docker |
| 处理公司敏感数据 | 本地受限容器或内网执行服务 |
| 面向陌生用户开放 | 专用沙箱/代码执行服务 |
| 需要复杂科学计算 | 预装依赖的容器镜像或托管运行时 |

判断重点不是“自己写还是调用 API”这一句，而是：谁负责语言运行时、谁负责隔离、谁负责数据传输、谁负责资源控制。

---

## 10. 面试级回答模板

如果面试官问：“你们项目的代码解释器是怎么实现的？”可以按四层回答：

1. **生成层**：CodeWizard 调用 LLM，根据研究数据和图表需求生成 Python。
2. **校验层**：清理代码，用 `compile()` 做语法检查，并用规则拦截明显危险模式。
3. **执行层**：在受限 globals 中通过 `exec()` 执行，捕获 stdout、stderr 和 matplotlib 图片。
4. **反馈层**：把结果写回 `code_executions` 和 `charts`，失败时把错误反馈给 LLM，最多自动修复重试三次。

接着主动说明限制：这是进程内简化沙箱，不能作为生产级安全隔离；生产环境应使用 Docker 或专用代码执行服务，增加网络、文件系统、CPU、内存和超时限制。
