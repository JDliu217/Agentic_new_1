# DeepResearch 学习手册：第 48 课

## CodeWizard：执行边界与失败自修复

CodeWizard 的能力来自两个部分共同作用：LLM 负责决定代码内容，Python 执行环境负责真正运行代码。两者缺一不可。

## 1. 一次代码分析的流程

```text
ResearchState 中的 data_points / 分析任务
  → LLM 生成 Python
  → 清理 Markdown 围栏和转义
  → compile() 语法检查
  → 危险模式检查
  → 受限 globals
  → exec()
  → stdout/stderr/图像
  → state["code_executions"] 和 state["charts"]
```

LLM 不会凭空产生真实计算结果；它只是生成一段候选程序。真正的结果取决于 Python 版本、预加载模块、输入数据、执行超时和运行环境。

## 2. 当前允许的执行环境

源码为代码准备了 pandas、numpy、matplotlib、seaborn 等能力，并限制或拒绝部分导入和危险调用。它还会设置非交互式绘图后端，将图表保存为 PNG 或转成 Base64。

这些限制是应用层逻辑，不是操作系统级隔离。

## 3. `compile()` 能做什么

```python
compile(code, '<string>', 'exec')
```

它主要检查 Python 语法是否能被编译，例如括号、缩进、语法结构错误。它不能证明：

- 代码没有读取敏感文件。
- 代码不会消耗无限 CPU 或内存。
- 代码不会绕过限制访问网络。
- 代码不会利用 Python 对象逃逸执行危险操作。

因此“编译成功”只代表语法可接受，不代表安全或业务正确。

## 4. 为什么正则拦截不够

项目会检查 `exec(`、`compile(`、`subprocess` 等明显危险模式，但正则匹配存在：

- 表达方式变形可以绕过简单字符串检查。
- Python 动态对象能力很复杂。
- 即使没有恶意代码，普通代码也可能死循环或申请巨大内存。
- 进程内执行可能影响后端主进程。

生产环境应使用独立容器或专用沙箱，并设置 CPU、内存、时间、网络和文件系统限制。

## 5. 失败后的自修复

如果代码执行失败，CodeWizard 会记录错误，把错误反馈给 LLM，让 LLM 生成修正版代码，再尝试执行。源码中设置了最大重试次数，重试信息会写入 `code_executions`。

```text
生成代码
  → 执行失败
  → 收集异常
  → LLM 修复
  → 再次 compile/检查/exec
```

这提高了演示场景下的成功率，但也带来成本和风险：每次重试都会再次调用模型，错误可能被掩盖，且不能把“自动修复成功”理解成“代码逻辑一定正确”。

## 6. LLM 与环境谁决定能力

可以这样区分：

```text
LLM：想做什么、写什么代码、怎样修改代码
执行环境：能否导入模块、拿到什么数据、能运行多久、能否访问网络和文件
```

LLM 很强但环境没有 pandas，代码仍会失败；环境很强但 LLM 生成错误代码，结果仍可能错误。最终能力是两者以及资源和安全策略共同决定的。

## 7. 本课练习

1. 为什么 `compile()` 通过不能证明代码安全？
2. 如果 LLM 生成了一个正确的 pandas 程序，但执行环境没有 pandas，会发生什么？
3. 为什么代码自修复最多重试几次，而不是无限重试？
4. 生产环境应该把执行隔离在哪些边界之外？
