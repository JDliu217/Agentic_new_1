# DeepResearch 学习手册：第 95 课

## 工程风险、可靠性与面试深挖

这一课的目标不是继续增加功能，而是学会判断：源码“能运行”之后，距离“可维护、可上线、可解释”还有多远。

阅读工程项目时，要同时问四个问题：

1. 代码实际做了什么？
2. 失败时会发生什么？
3. 用户是否可能看到错误用户的数据？
4. 这个实现能不能承受真实流量和真实攻击？

## 1. 研究请求缺少直接的用户依赖

证据文件：

```text
backend/app/router/research_router.py
```

`POST /research/stream` 的路由参数包含 `ResearchRequest` 和服务依赖，但没有像知识库、记忆、数据库接口那样直接声明必需的 `current_user`。

这说明：

```text
请求进入研究接口
→ 校验研究问题
→ 根据 version 选择 V1/V2
→ 传入 session_id
```

但“这个 session_id 是否属于当前登录用户”不能仅凭该路由签名得到保证。

### 影响

- 未登录请求可能进入研究链路，取决于其他层是否补充校验。
- 攻击者可能尝试提交别人的 `session_id`。
- `/resume/{session_id}`、检查点查询和删除接口也需要明确用户归属校验。

### 修复方向

1. 在所有研究、检查点和恢复接口中加入必需的认证依赖。
2. 从 JWT 得到用户身份，不接受客户端传入的 `user_id` 作为可信来源。
3. 查询检查点时同时使用 `session_id` 和 `user_id` 条件。
4. 对旧数据和没有归属关系的检查点返回统一的 404 或授权错误。

## 2. CORS 配置过宽

证据文件：

```text
backend/app/app_main.py
```

当前配置允许所有来源，同时开启凭证，并允许所有方法和请求头：

```text
allow_origins=["*"]
allow_credentials=True
allow_methods=["*"]
allow_headers=["*"]
```

开发环境中这样做方便调试，但生产环境应使用明确的前端域名列表。

### 影响

如果认证方式依赖浏览器凭证或跨域携带身份信息，任意来源都可能扩大攻击面。CORS 也不能替代后端权限校验；即使浏览器限制了页面读取响应，恶意请求仍可能触发后端逻辑。

### 修复方向

```text
ALLOWED_ORIGINS=https://前端正式域名
```

启动时读取配置，校验域名格式，并为本地开发和生产环境使用不同配置。

## 3. 配置中存在硬编码密钥风险

证据文件：

```text
backend/app/service/dr_g.py
backend/app/service/config.py
```

V1 代码和旧兼容配置存在把 API key 写成默认字符串的实现。即使这些密钥已经失效，也不应保留这种模式。

### 影响

- 密钥可能进入 Git 历史、日志、镜像和备份。
- 多人共享代码时无法区分开发、测试和生产凭证。
- 环境变量缺失时，程序可能悄悄使用错误凭证，而不是立即失败。

### 修复方向

1. 删除代码中的真实或疑似真实密钥。
2. 未配置关键密钥时启动失败，或明确把对应功能标记为不可用。
3. 使用 `.env.example` 保存变量名，不保存变量值。
4. 已经暴露过的密钥应立即吊销和轮换；仅删除源码不能撤销已泄露凭证。

## 4. V2 恢复不是严格的节点级断点续跑

证据文件：

```text
backend/app/service/deep_research_v2/graph.py
```

`run()` 在 `resume=True` 时会尝试加载检查点，然后固定进入 `_run_simplified(state)`。源码中 LangGraph 执行分支被保留但没有作为当前默认路径调用。

因此当前语义更接近：

```text
读取旧状态
→ 带着旧状态重新进入手写流程
```

而不是：

```text
识别上次成功的节点
→ 从该节点继续执行
→ 跳过已经完成的节点
```

### 影响

- 可能重复搜索、重复调用 LLM 或重复写入结果。
- 断点恢复的耗时和费用不一定比重新开始低。
- 用户界面显示“已恢复”不代表后端实现了精确续跑。

### 修复方向

为每个节点记录可恢复的阶段、输入版本和输出版本；恢复时根据状态机选择下一个未完成节点。需要保证节点幂等，避免重复写入和重复发送事件。

## 5. 异常被吞掉会降低可观测性

项目中多个外部服务调用在异常后返回空列表、`None` 或错误对象。例如搜索、Embedding、DocMind 和行业采集服务都有降级逻辑。

这种处理不一定错误。关键是必须区分：

| 情况 | 合理行为 |
|---|---|
| 外部搜索暂时失败 | 记录错误，允许明确标记为“搜索不可用” |
| 没有搜索结果 | 返回空结果，但告诉上层这是正常空结果 |
| Embedding 失败 | 不应伪装成已经完成向量入库 |
| 数据库失败 | 通常应终止当前事务并返回可定位错误 |
| 使用 Mock 数据 | 必须在响应和日志中明确标识 |

### 排错原则

不要只看最终报告是否生成。应同时检查：

```text
请求日志
→ 外部调用状态码
→ 原始异常
→ 降级分支
→ ResearchState 字段
→ SSE 事件
→ 前端展示
```

## 6. Mock 数据会改变“成功”的含义

Text2SQL、部分测试接口和外部服务缺失时存在 Mock 或 fallback 路径。

如果数据库不可用但接口仍返回一组数据，接口层面的 HTTP 200 只能证明“程序返回了响应”，不能证明“查询了真实数据库”。

### 作为学习者必须区分三种证据

1. **静态证据**：源码中存在某个函数或分支。
2. **构建证据**：代码可以通过编译或前端打包。
3. **运行证据**：真实数据库、Redis、Milvus、LLM 和外部 API 都参与了一次成功请求。

当前项目已经有较强的静态和构建证据，但完整外部依赖端到端证据仍需要可用的运行环境。

## 7. BackgroundTasks 不等于可靠任务队列

知识库解析、附件处理和部分采集任务使用 FastAPI `BackgroundTasks`。

它适合短小、低风险的请求后处理，但不等于独立的任务系统：

- 进程重启可能丢失任务。
- 没有天然的重试、并发控制和持久化队列。
- 长时间的 DocMind、Embedding 或外部 API 调用可能占用应用资源。

生产化方向通常是独立 worker 加持久化队列，任务状态写入数据库，并提供重试、超时和死信处理。

## 8. CodeWizard 的可靠性边界

CodeWizard 当前链路是：

```text
LLM 生成 Python
→ compile 语法检查
→ 正则危险模式检查
→ 受限 globals 执行
→ 捕获 stdout、stderr 和图片
```

这适合教学和受控演示，但正则过滤和进程内 `exec` 不能提供生产级隔离。资源耗尽、绕过过滤、文件访问、网络访问和线程强制终止都需要单独治理。

生产方案应使用独立进程或容器，并限制：

```text
CPU、内存、运行时间、网络、文件系统、系统调用和进程权限
```

## 9. 面试官会怎样追问

### 题目一

为什么 `POST /research/stream` 默认进入 V2，而 `GET /research/stream` 默认进入 V1？

**回答要点：** 查看请求方法对应的路由函数和 `version` 默认值；不能只看 URL 路径。

### 题目二

如果用户 A 把用户 B 的 `session_id` 放到恢复接口中，应该在哪里阻止？

**回答要点：** 认证依赖得到当前用户，数据库查询同时按会话 ID 和用户 ID 过滤；不能只依赖前端隐藏按钮。

### 题目三

为什么检查点加载成功仍不能证明实现了断点续跑？

**回答要点：** 需要看恢复后从哪个节点开始；当前源码加载旧状态后仍进入 `_run_simplified()`，可能重新执行前置阶段。

### 题目四

为什么 HTTP 200 的 Text2SQL 响应不能证明查询了真实数据？

**回答要点：** 必须确认数据库连接、实际 SQL、执行日志和是否进入 `_get_mock_data()` fallback。

### 题目五

为什么 CodeWizard 的 `compile()` 和危险字符串检查不等于安全沙箱？

**回答要点：** 语法检查只判断代码能否解析，正则检查可绕过，进程内执行没有真正的权限、资源和系统调用隔离。
