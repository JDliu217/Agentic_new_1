# DeepResearch 性能与稳定性检查表

## 1. 请求入口

- [ ] 研究请求有明确的超时时间。
- [ ] 相同研究任务不会因为重复点击而无限创建后台任务。
- [ ] 请求参数在进入 Agent 前已经完成校验和规范化。
- [ ] 每个请求都有可追踪的研究 ID 或关联 ID。
- [ ] 认证失败和业务失败能与服务器内部异常区分开。

## 2. Agent 编排

### 并发

确认哪些 Agent 可以并行，哪些 Agent 必须等待前置结果。并行任务需要设置数量上限，避免一次研究请求占满线程、连接池或模型额度。

### 超时

为每次 LLM 调用、搜索调用、数据库访问和代码执行设置独立超时。总研究超时不能只依赖单个外部调用的超时。

### 重试

重试只用于临时性错误，并设置次数、退避时间和最大总耗时。对参数错误、权限错误和内容错误不应盲目重试。

## 3. SSE 稳定性

- [ ] 事件格式固定，前端和后端使用同一字段契约。
- [ ] 事件发送顺序不会因为并发任务而失控。
- [ ] 客户端断线时，后台任务是否继续有明确策略。
- [ ] 客户端重连时不会重复启动同一个研究。
- [ ] 失败、取消和完成都有明确的终止事件。
- [ ] 长时间没有内容时仍能发送心跳，避免代理层断开连接。

## 4. 数据库与向量库

### 数据库

检查连接池大小、事务边界、提交时机和失败回滚。最终报告只有在持久化成功后才应向前端发送“已完成”状态。

### Milvus

检查集合是否提前创建、向量维度是否一致、插入后是否完成索引，以及查询使用的集合和过滤条件是否正确。上传状态和向量库状态需要分别记录。

## 5. CodeWizard 安全与资源

如果代码执行仍在当前进程内完成，需要特别记录以下限制是否存在：

- 执行超时
- 输出大小上限
- 内存和 CPU 限制
- 文件系统隔离
- 网络访问控制
- 环境变量过滤
- 进程和子进程限制

没有这些限制时，性能问题和安全问题可能同时发生。

## 6. 观测指标

建议至少记录：

| 指标 | 用途 |
| --- | --- |
| 研究总耗时 | 判断用户体验和整体退化 |
| 各 Agent 耗时 | 找到慢节点 |
| LLM 调用次数和 token | 控制成本和异常循环 |
| 搜索成功率 | 判断外部检索稳定性 |
| SSE 断开率 | 判断实时交互质量 |
| 失败类型分布 | 区分代码、配置和外部依赖问题 |
| 报告持久化成功率 | 判断完成状态是否可信 |
